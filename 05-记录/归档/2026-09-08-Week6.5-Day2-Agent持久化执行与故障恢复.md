# Week 6.5 Day 2 归档：Agent 持久化执行与故障恢复（2026-09-08）

## 今日完成

1. 区分对话记忆、业务数据和 Agent 执行状态。
2. 新增 `AgentRun`、`AgentStep`、`AgentRunStatus`，用结构化状态记录计划、已完成步骤、下一步和错误。
3. 新增 `AgentCheckpointStore` 与内存实现，覆盖保存、恢复、幂等键索引、租户隔离、删除和过期清理。
4. 新增 `IdempotentToolExecutor`，同一租户、同一步骤幂等键只真正执行一次，成功结果可重放。
5. 新增 `WorkflowApprovalService`，Agent Run 在人工批准前保持暂停且不产生副作用。
6. 新增 `DurableOrderWorkflowService`，实现订单更新、通知、失败存档、恢复和订单补偿。
7. `AuditLogService` 注册为 Spring Bean，审计状态增加 FAILED、COMPENSATED。
8. 全局规则增加“用通俗易懂、形象且准确的话讲解每日知识”。
9. 补充失败重试计数：第一次失败后 `attempts=1`，第二次重试成功后 `attempts=2`；尝试次数不等于成功次数。
10. 记录生产风险：下游已成功但响应丢失时，本地重试可能产生重复副作用，幂等键必须继续传递到下游系统。

## 企业联调结果

场景：把 O1003 从 PENDING 改成 SHIPPED，然后通知用户。

1. DeepSeek 生成白名单计划 `UPDATE_ORDER,SEND_NOTIFICATION`。
2. 人工批准前订单更新次数为 0。
3. 批准后订单更新成功，Checkpoint 指向 SEND_NOTIFICATION。
4. 通知第一次模拟失败，Agent Run 保存为 FAILED。
5. 新建 Workflow 服务实例，从 SEND_NOTIFICATION 继续并完成。
6. 订单更新总计 1 次，通知尝试 2 次、成功 1 次。
7. 相同业务幂等键再次发起请求，返回原来的已完成 Agent Run。

## 边界

- 当前 Checkpoint、审批和幂等结果为内存实现，只验证恢复协议，不能抵抗整个 JVM 重启。
- 生产环境需要 MySQL/Redis/工作流引擎、并发版本控制、持久化幂等结果和下游幂等支持。
- 补偿不是数据库回滚，必须根据当前业务状态执行，且补偿本身也可能失败。
