## 2026-08-11

- 日期：2026-08-11
- 问题描述：Java 编译报「非法字符: '\ufeff'」
- 报错 / 现象：maven-compiler 编译失败，`EnterpriseAgentApplication.java:[1,1] 非法字符: '\ufeff'`
- 排查过程：PowerShell `Set-Content -Encoding UTF8`（Windows PowerShell 5.1）会写入 UTF-8 BOM，Java 源码不接受
- 解决方案：用 `[System.IO.File]::WriteAllText(path, content, (New-Object System.Text.UTF8Encoding($false)))` 写无 BOM UTF-8
- 涉及技术：PowerShell / Java / Maven

- 涉及技术：LangChain4j 1.x / Java

## 2026-08-13
- 日期：2026-08-13
- 问题描述：SSE 流式输出中文乱码
- 报错 / 现象：/chat/stream 返回的 data: 内容中文变成 â?¤ 等乱码；MockMvc 断言失败
- 排查过程：SseEmitter 响应默认按 ISO-8859-1 编码字符串，中文（UTF-8 字节）被当 Latin-1 解码
- 解决方案：控制器里显式 response.setCharacterEncoding("UTF-8")，并用 produces="text/event-stream;charset=UTF-8"
- 涉及技术：Spring MVC / SseEmitter / SSE / 编码

- 日期：2026-08-14
- 问题描述：DeepSeek 不支持 LangChain4j 的 json_schema 原生结构化输出
- 报错 / 现象：请求带 response_format.type=json_schema 时返回 {"error":{"message":"This response_format type is unavailable now","type":"invalid_request_error"}}
- 排查过程：先用 mock 单测通过，真实联调暴露；确认是模型服务端不支持该 response_format 类型
- 解决方案：默认改用 json_object 模式（ResponseFormat.JSON）+ system prompt 写明 JSON 结构 + 服务端 Jackson 解析并校验必填字段；保留 json_schema 模式供 OpenAI 系模型使用
- 涉及技术：LangChain4j / DeepSeek / JSON Schema

- 日期：2026-08-16
- 问题描述：不可重试错误被降级逻辑吞掉，返回了空结果
- 报错 / 现象：测试「不可重试错误应快速失败」失败——InvalidRequestException 未抛出，callWithFallback 返回 null
- 排查过程：降级逻辑对所有异常都切备用模型，备用模型未 stub 返回 null；本质是「参数/认证类错误降级无意义且掩盖问题」
- 解决方案：只有 isRetryable(e) 为真才重试/降级；NonRetriableException 与 4xx 直接抛出
- 涉及技术：容错设计 / 重试策略

## 2026-08-25

- 日期：2026-08-25
- 问题描述：MCP stdio 联调时客户端报「Ignoring message received because it is not valid JSON」
- 报错 / 现象：真实启动 `OrderMcpServer` 子进程后，`StdioMcpTransport` 收到的 stdout 流里混入了 Logback 的 INFO 日志，协议解析失败
- 排查过程：MCP stdio 规定 stdout 只能传输 JSON-RPC；而 Java 的 Logback 默认把 INFO 打到 stdout，服务端启动日志污染了协议流
- 解决方案：为 Server 子进程单独配置 `logback-mcp.xml`，把 `ConsoleAppender` 的 `target` 设为 `System.err`；`OrderMcpServer.main()` 里通过 `logback.configurationFile` 指定
- 涉及技术：MCP / stdio / Logback / stdout 协议流

- 日期：2026-08-25
- 问题描述：MCP stdio 客户端 `close()` 一直卡住，测试不结束
- 报错 / 现象：`DefaultMcpClient.close()` 卡在 `JsonRpcIoHandler.close()` 的 `BufferedInputStream.close()`，最终 Maven 测试超时
- 排查过程：`StdioMcpTransport.close()` 会先关 IO 流再销毁进程；而 `OrderMcpServer.main()` 里的 `Thread.currentThread().join()` 让 Server 进程永不退出，形成「关流等进程退出 / 进程等流关闭」的死锁
- 解决方案：去掉 `main()` 里的 `join()`，让 main 正常返回；Server 的收包线程是非守护线程会维持进程存活，stdin 关闭后自然退出
- 涉及技术：MCP / stdio / Java 进程生命周期 / 死锁
