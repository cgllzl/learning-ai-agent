# Week 6.5：Agent 企业实战前补缺学习清单

> 阶段位置：Week 6 完成后、Week 7～8 企业项目实战前
> 建议周期：6 个学习日
> 核心目标：不再扩展新框架，只补齐企业 Agent 必需的控制、恢复、安全、评估和 MCP 新规范知识。

## 一、学习规则

- [ ] 主技术栈继续使用 Java 21 + Spring Boot + LangChain4j + DeepSeek，不切换到其他 Agent 框架。
- [ ] 每天新增知识都写一篇知识库笔记，包含概念、关键代码、企业例子、测试方法和完成标准。
- [ ] 每天至少有一个贴近企业生产的例子，不能只做教学 Demo。
- [ ] 每天至少有一个真实调用 DeepSeek 的 `xxxLiveTest`，并在笔记中写清运行命令。
- [ ] 每天同时提供不调用大模型的本地自动化测试，保证核心规则可以稳定回归。
- [ ] 如果当天无法访问真实大模型，记录具体原因，并提供可运行的本地替代验证。
- [ ] 所有有副作用的 Tool 都要考虑权限、参数校验、幂等、审计、超时和失败恢复。

## 二、Day 1：Agent 与 Workflow 的边界及控制流 ✅

> 状态：2026-09-06 已完成；11 个离线测试和 2 个真实 DeepSeek LiveTest 通过。

### 必须掌握

- [x] 能解释 Workflow 与 Agent 的区别：固定代码路径 vs 模型动态决策。
- [x] 能根据可预测性、风险、成本和任务变化程度选择二者，而不是所有场景都使用自主 Agent。
- [x] 复习 Sequential、Supervisor，补齐 Conditional、Parallel、Loop、Handoff 的适用场景。
- [x] 理解任务分解、共享状态、分支条件、循环退出条件和结果合并。
- [x] 给 Agent 设置最大步骤数、最大循环次数、超时、Token/费用预算和明确终止状态。
- [x] 不依赖模型输出隐藏思维过程；只保存可审计的计划步骤、工具调用和业务状态。

### 实践任务

- [x] 学习例子：实现“问题分类 → 对应专家处理”的 Conditional Workflow。
- [x] 企业例子：实现“企业工单分诊 → 订单/知识库/人工客服分支”。
- [x] 增加一个有限 Loop：答复未通过业务规则时最多修改 2～3 次，超限后转人工。
- [x] 为每个分支定义结构化输入、结构化输出和失败状态。
- [x] 编写 `ConditionalWorkflowTest`、`LoopWorkflowTest`。
- [x] 编写 `AgentWorkflowLiveTest`，真实调用 DeepSeek 验证分诊和有限循环。
- [x] 在知识库新增“Agent 与 Workflow 边界及控制流”笔记，并写清测试命令。

### 完成标准

- [x] 正常请求能进入正确分支。
- [x] 无法分类的请求不会随意调用高风险 Tool，而是降级或转人工。
- [x] Loop 一定能在限定次数内终止。
- [x] 可以说明为什么该流程不应全部交给模型自由规划。

## 三、Day 2：执行状态持久化、恢复、幂等与补偿

### 必须掌握

- [ ] 区分对话记忆、业务数据和 Agent 执行状态。
- [ ] 理解 Agent Run、Step、Checkpoint、状态机和恢复点。
- [ ] 理解服务崩溃、网络超时和人工审批暂停后的恢复流程。
- [ ] 理解幂等键，避免恢复或重试时重复改订单、重复退款、重复发送通知。
- [ ] 理解补偿操作与数据库事务的区别，以及跨 Agent 失败时为什么需要反向补偿。
- [ ] 明确状态的租户隔离、过期、删除和审计要求。

### 实践任务

- [ ] 学习例子：把两步任务的进度保存到内存版 Checkpoint Store，并从中断步骤恢复。
- [ ] 企业例子：订单状态修改流程在“写订单成功、发通知失败”后恢复，确保订单不被重复修改。
- [ ] 设计 `AgentRun`、`AgentStep`、`AgentRunStatus` 和 `AgentCheckpointStore`。
- [ ] 给有副作用的 Tool 增加幂等键和执行结果记录。
- [ ] 为可逆操作设计补偿动作；不可逆操作必须在执行前审批。
- [ ] 编写 `DurableAgentWorkflowTest`，模拟崩溃、重启、重复请求和补偿失败。
- [ ] 编写 `DurableAgentWorkflowLiveTest`，真实调用 DeepSeek 生成或选择步骤，再验证本地恢复逻辑。
- [ ] 在知识库新增“Agent 持久化执行与故障恢复”笔记，并写清测试命令。

### 完成标准

- [ ] 同一个幂等键重复执行不会产生第二次业务副作用。
- [ ] 中途失败后能从最近 Checkpoint 恢复，而不是整条链路重跑。
- [ ] 人工审批等待期间可以安全暂停，批准后继续。
- [ ] 跨租户不能读取或恢复其他租户的 Agent Run。

## 四、Day 3：Agentic AI 专项安全

### 必须掌握

- [ ] 阅读 OWASP Agentic Top 10 2026 总览。
- [ ] 理解 Agent Goal Hijack，特别是来自 RAG 文档、邮件、网页和 Tool 返回值的间接 Prompt Injection。
- [ ] 理解 Tool Misuse、Tool Poisoning、工具名仿冒和危险工具链组合。
- [ ] 理解 Identity & Privilege Abuse：委托时权限扩大、跨 Agent 混淆代理、执行前权限已变化。
- [ ] 理解 Memory & Context Poisoning，以及污染内容为什么可能跨会话长期生效。
- [ ] 理解 Insecure Inter-Agent Communication、Cascading Failures 和 Agentic Supply Chain 风险。
- [ ] 理解“最小权限”之外的“最小自主权”：能用固定 Workflow 的高风险操作不交给模型自由规划。

### 实践任务

- [ ] 为当前企业 Agent 画一张简化威胁模型：用户、模型、RAG、Memory、Tool、MCP、子 Agent、外部系统。
- [ ] 学习例子：构造一段含隐藏指令的检索文本，验证系统不会把资料内容当作系统指令。
- [ ] 企业例子：恶意供应商文档要求 Agent 导出客户数据并调用外部 Tool，安全层必须阻断。
- [ ] 增加 Tool 调用前的 Intent Gate：重新校验用户目标、工具、参数、租户、权限和风险等级。
- [ ] 对跨 Agent 消息使用结构化数据，携带原始用户、租户、授权范围和 Trace ID。
- [ ] 对第三方 Tool/MCP 使用允许列表、版本固定、工具描述检查和出站目标限制。
- [ ] 编写 `AgenticSecurityGuardTest`，覆盖间接注入、工具投毒、记忆污染和跨 Agent 越权。
- [ ] 编写 `IndirectPromptInjectionLiveTest`，真实调用 DeepSeek 验证攻击链被阻断。
- [ ] 在知识库新增“OWASP Agentic Top 10 与项目威胁模型”笔记，并写清测试命令。

### 完成标准

- [ ] 用户输入、RAG 内容、Memory 内容、Tool 输出和 Agent 消息全部按不可信数据处理。
- [ ] 高风险 Tool 执行前会重新鉴权，不能只沿用流程开始时的权限结果。
- [ ] 恶意文档无法改变 Agent 原始目标或触发数据外传。
- [ ] 所有拦截、审批和工具调用都有审计记录。

## 五、Day 4：Agent 轨迹评估与稳定性评估

### 必须掌握

- [ ] 区分最终答案评估、任务结果评估和执行轨迹评估。
- [ ] 在关键词正确性之外增加：工具选择、参数正确性、调用顺序、权限合规、任务是否真实完成。
- [ ] 理解模型输出的随机性；重要用例需要重复运行并统计成功率，而不是只跑一次。
- [ ] 建立独立留出集，避免为了通过现有用例写死答案或 Prompt。
- [ ] 联合比较质量、Token、成本、延迟和步骤数。
- [ ] 为 Single-Agent 与 Multi-Agent 建立相同输入和相同完成标准。

### 实践任务

- [ ] 设计 `AgentTrajectory`：记录 Agent、步骤、Tool、参数摘要、结果状态、耗时和 Token。
- [ ] 设计 `TrajectoryEvaluator`：检查必需步骤、禁止步骤、工具参数和审批顺序。
- [ ] 学习例子：判断“答案正确但调用了错误 Tool”的用例应失败。
- [ ] 企业例子：订单查询不得调用写操作，订单修改必须先审批再调用更新 Tool。
- [ ] 对关键用例重复运行至少 5 次，输出成功率、平均成本、P95 延迟和平均步骤数。
- [ ] 比较同一工单任务的 Single-Agent 与 Multi-Agent，记录质量和成本差异。
- [ ] 编写 `TrajectoryEvaluatorTest` 和 `AgentComparisonReportTest`。
- [ ] 编写 `AgentTrajectoryEvaluationLiveTest`，真实调用 DeepSeek 生成评估数据。
- [ ] 在知识库新增“Agent 轨迹、稳定性与成本联合评估”笔记，并写清测试命令。

### 完成标准

- [ ] 回答文本正确但行为违规时，评估必须失败。
- [ ] 关键用例有重复运行统计，而不是单次成功结论。
- [ ] CI 能使用离线轨迹用例稳定回归；真实模型评估单独运行。
- [ ] 能用数据回答 Multi-Agent 是否比 Single-Agent 更好。

## 六、Day 5：MCP 新规范与第三方 MCP 安全接入

### 必须掌握

- [ ] 对比项目当前登记的 MCP 2025-06-18 与 MCP 2026-07-28。
- [ ] 理解新规范的无会话核心、每请求能力信息和 `server/discover`。
- [ ] 理解 MRTR 的 `input_required`，以及工具执行中补参数、确认和审批的用途。
- [ ] 理解工具/资源列表缓存、Header 路由、Tasks 扩展及长耗时任务取消。
- [ ] 了解 Roots、Sampling、Logging 和旧 HTTP+SSE 传输的弃用方向。
- [ ] 理解远程 MCP 的 OAuth、Token Audience、最小 Scope、禁止 Token Passthrough 和凭证隔离。
- [ ] 确认当前 LangChain4j/Java MCP SDK 实际支持的规范版本，不盲目迁移未支持功能。

### 实践任务

- [ ] 输出一张“旧规范 → 新规范 → 当前 Java 支持情况”的兼容性表。
- [ ] 学习例子：继续保留现有 stdio MCP，验证当前功能没有因资料更新而误判。
- [ ] 企业例子：评估一个第三方订单/CRM MCP Server，只开放只读工具，再逐步开放写操作。
- [ ] 接入第三方 MCP 前检查来源、版本、工具列表、参数 Schema、权限范围、网络出口和日志敏感信息。
- [ ] 工具列表发生变化时做差异检查；新增高危工具不得自动对 Agent 开放。
- [ ] 编写 `McpCompatibilityTest` 和 `McpToolTrustPolicyTest`。
- [ ] 条件允许时编写 `ThirdPartyMcpLiveTest`，真实调用 DeepSeek + 第三方 MCP 完成一次只读任务。
- [ ] 如果 Java SDK或网络条件不支持，记录具体原因，并用本地 MCP Server 完成相同的安全策略验证。
- [ ] 更新 Week 4、Week 7～8 的 MCP 资料链接和版本说明。
- [ ] 在知识库新增“MCP 2026-07-28 变化与第三方接入安全”笔记，并写清测试命令。

### 完成标准

- [ ] 能说明当前项目实现支持哪一版 MCP、哪些新能力暂不支持。
- [ ] 第三方 MCP 默认不能获得所有 Tool 和所有业务权限。
- [ ] 未审核的新工具或工具描述变化不会自动进入 Agent 可调用列表。
- [ ] 远程 MCP 凭证不会透传给下游服务或写入日志。

## 七、Day 6：Agent Skill 设计、测试与治理

### 必须掌握

- [ ] 能区分 Prompt、Tool、MCP、Workflow、Skill 和 Plugin 的职责。
- [ ] 理解 Skill 是可复用的任务 SOP，由指令、参考资料、可选脚本和资源组成。
- [ ] 掌握 `SKILL.md` 的 `name`、`description`、正文指令和目录结构。
- [ ] 理解显式调用、根据描述自动触发和渐进式内容加载。
- [ ] 理解 Skill 的版本、权限、脚本供应链、指令冲突和过期知识风险。
- [ ] 理解 Skill 需要同时评估触发准确性和任务执行质量。

### 实践任务

- [ ] 分析两个成熟 Skill，记录触发边界、资源组织和测试方式。
- [ ] 学习例子：创建一个只包含说明和示例的最小 Skill。
- [ ] 企业例子：创建“企业订单售后处理 Skill”，包含租户、权限、审批、审计和输出 SOP。
- [ ] 准备至少 5 个应触发和 5 个不应触发的真实用户问题。
- [ ] 对比有 Skill 与无 Skill 时的步骤完整率、违规次数和输出一致性。
- [ ] Skill 自带脚本只能做确定性辅助工作，不能绕过 Tool 权限或人工审批。
- [ ] 条件允许时在 Codex 中验证显式与自动触发；Java 项目只做必要的 Skill 选择/加载实验，不重造完整平台。
- [ ] 编写真实大模型联调或可重复执行的 Skill 评估命令，并记录结果。
- [ ] 在知识库新增“Agent Skill 设计、测试与治理”笔记。

### 完成标准

- [ ] 能说明 Skill 为什么不是长 Prompt，也不是另一种 Tool。
- [ ] 一个企业 Skill 可以被稳定触发，并且不会被无关请求误触发。
- [ ] Skill 的业务步骤、权限边界和完成标准可审计。
- [ ] Skill 更新有版本记录和回归测试。

## 八、企业项目期间继续完成的内容（不阻塞开工）

- [ ] 把 Memory 和 Agent Run 持久化到 Redis/MySQL，验证服务重启后恢复。
- [ ] 接入真正的 OpenTelemetry/Micrometer，而不只使用项目内的最小 Trace 实现。
- [ ] 增加异常告警、成本预算告警、循环调用告警和异常工具序列告警。
- [ ] 把 RAG 从内存向量库切换到 pgvector/Qdrant，并实现文档级租户权限过滤。
- [ ] 增加 PDF/Word 解析、文档更新/删除、索引重建和数据保留策略。
- [ ] 工具数量扩大后再学习 Tool Search/渐进式工具披露，当前少量 Tool 无需提前复杂化。

## 九、暂时不学，防止范围失控

- [ ] 不同时学习 LangGraph、CrewAI、AutoGen 等其他主框架。
- [ ] 不在第一个企业项目之前实现 Voting、Debate、BDI、Agent Society 等高级多 Agent 模式。
- [ ] 不把训练模型、微调、Transformer 源码作为当前 Agent 工程前置条件。
- [ ] 不为了追逐最新 MCP 规范强行替换尚未兼容的 Java SDK。
- [ ] 不使用复杂 Agent 架构，除非评估数据证明它优于简单 Workflow 或 Single-Agent。
